# 沐龙量化交易平台 — 项目介绍与面试题库

> 基于当前仓库真实架构整理（`backpack_quant_trading/` + Docker + GitHub Actions）。  
> 用途：项目说明 / 简历口述 / 技术面准备。

## 一、项目是什么

**沐龙量化交易平台**是一套「交易后台 + 策略矩阵 + 多市场监控 + 钉钉多 Agent 协作」的一体化系统。

它不是单纯回测脚本，而是把以下能力做成可部署、可运维的产品：

| 能力 | 说明 |
|------|------|
| 实盘与策略 | 网格、自适应多空、双周期趋势、多标的动量策略等 |
| 多市场 | 加密货币（OKX / Binance / ccxt 等）、A 股（akshare）、美股/指数（Massive/Polygon） |
| 管理后台 | React Web：登录、大盘、策略页、OKX 控制台、Agent 记忆、学习中心 |
| 钉钉 Agent | Stream 机器人：分析师编排、评分纠偏、小管家运维、A 股 AI 信号推送 |
| AI 增强 | DeepSeek 结构化决策、Chroma RAG 偏好学习、小沫数字人（ASR/TTS） |
| 工程化 | Docker Compose 多进程、测试机/正式机分流、禁止热更的 CI/CD |

典型用户路径：

1. 网页配置策略 / 监视任务  
2. API 拉行情、跑策略、写 MySQL  
3. 信号或巡检结果推钉钉  
4. 群里 @机器人纠偏 → 进 RAG / 草稿 → 人工确认后影响后续风格  
5. 正式变更走 GitHub Actions 全量部署，不在生产机改代码

## 二、整体架构（简图）

```
┌─────────────────┐     ┌──────────────────────────────────────┐
│  React + Vite   │────▶│  FastAPI (Gunicorn + UvicornWorker)  │
│  管理后台 :8100 │     │  交易 / 策略 / 监控 / Agent API       │
└─────────────────┘     └──────────────┬───────────────────────┘
                                       │
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
   MySQL 8                      ChromaDB                     交易所 / 行情
 (业务配置/状态)              (评分反馈/偏好RAG)            OKX·Binance·akshare·Massive
         ▲
         │
┌────────┴────────┐     ┌──────────────────┐     ┌─────────────────────┐
│ webhook :8005   │     │ dingtalk-agent   │────▶│ 钉钉 Stream / Webhook│
│ TradingView 等  │     │ 编排·评分·小管家 │     │ ActionCard / 群点评  │
└─────────────────┘     └──────────────────┘     └─────────────────────┘
```

Compose 核心服务：

- `api`：HTTP API + 静态前端  
- `webhook`：外部信号入口  
- `dingtalk-agent`：钉钉长连接 Agent（内存更高，挂 Chroma 模型缓存）  
- `mysql`：仅本地/测试 profile；正式机多用外部 MySQL  

正式服策略：**禁止** `docker cp` / 热更；**唯一路径**为本地改 → push → Actions「Deploy to Prod ECS」。

## 三、技术栈与选型理由

### 3.1 后端

| 技术 | 用途 | 为什么选 |
|------|------|----------|
| **Python 3.11** | 主语言 | 量化生态（pandas/numpy/ta/ccxt）成熟；Agent/LLM SDK 最全；团队迭代快 |
| **FastAPI** | HTTP API | 异步友好、类型注解、自动 OpenAPI；适合大量路由（交易/监控/策略/Agent） |
| **Gunicorn + UvicornWorker** | 生产进程 | 多 worker 稳妥；与 FastAPI/ASGI 原生配合；容器内可限制 worker 数控内存 |
| **SQLAlchemy 2 + PyMySQL + MySQL 8** | 业务库 | 交易配置、任务状态需要事务与查询；MySQL 运维熟悉、ECS 常见 |
| **pandas / numpy / ta / numba** | 行情与指标 | 策略与回测刚需；numba 可加速热点计算 |
| **LightGBM + sklearn** | 短线涨跌辅助 | 表格特征场景效果稳、训练快，适合 3～5 日类任务 |
| **ccxt + 各所 SDK** | 多交易所 | 统一封装降低接入成本；特殊链路（OKX Agent、Hyperliquid 等）可单写 |
| **akshare** | A 股数据 | 国内常用、覆盖面够一期信号/基本面缓存 |
| **dingtalk-stream** | 群内交互 | 比纯 Webhook 更适合「@回复、收评、长连接」Agent 体验 |
| **ChromaDB** | 向量记忆 | 嵌入式、无需另起向量集群；适合偏好/点评级 RAG；小内存可 hash 嵌入兜底 |
| **DeepSeek（JSON 模式）** | LLM 决策 | 性价比高；强制 JSON 降低解析失败；适合评分/分析师/数字人 |
| **edge-tts** | 小沫 TTS | 无需自建语音服务，云端女声够用 |

### 3.2 前端

| 技术 | 用途 | 为什么选 |
|------|------|----------|
| **React 18** | SPA | 组件生态强；策略页/控制台交互复杂时好拆 |
| **Vite 5** | 构建 | 开发热更快；产物简单，适合打进 Docker |
| **React Router 6** | 路由 | 策略矩阵多页面标准方案 |
| **Axios** | HTTP | 拦截器做鉴权/错误统一处理 |
| **ECharts** | K 线/图表 | 金融可视化成熟，标注买卖点方便 |
| **Tailwind** | 样式 | 后台页快速布局 |
| **Three.js（可选）** | 数字人相关 | 形象/氛围；非交易主路径 |

> 构建策略：在 **GitHub Actions** 预构建 `frontend/dist`，ECS 镜像**不再跑 npm**（小内存易 OOM：`Exit handler never called` / `vite not found`）。

### 3.3 基础设施与 CI/CD

| 技术 | 用途 | 为什么选 |
|------|------|----------|
| **Docker + Compose** | 多进程隔离 | api / webhook / dingtalk-agent 内存与依赖不同；一键起停 |
| **阿里云 ECS** | 运行环境 | 国内网络、钉钉与行情代理可控 |
| **GitHub Actions** | CI/CD | 见下一节专项说明 |
| **SCP + SSH 远程脚本** | 发版落地 | Actions 打包 → 传到 `/tmp` → `remote-ci.sh` 解压 Compose 构建 |
| **版本标签 + 回滚** | 可回退发布 | 每次 deploy 打 `backpack-quant:<version>`，归档 tgz；Actions 可选 rollback |
| **Swap 保障脚本** | 小内存保活 | 无 swap 时 MySQL/构建易被 OOM |

### 3.4 为什么选 GitHub Actions（而不是 Jenkins / 自建 GitLab CI / 纯 SSH 手推）

结合本仓库实际约束，选型逻辑如下：

1. **代码已在 GitHub**  
   与仓库同源，权限、审计、Secrets、分支保护一套搞定，少维护第二套 CI 主机。

2. **正式服必须「全量可复现」**  
   曾因热更导致「路由新、策略旧、前端 dist 回退」。Actions 强制：checkout →（前端构建）→ 打 tar → 远端全量 `compose build`，版本一致。

3. **构建机与运行机职责分离**  
   - Actions（ubuntu-latest）：内存充足，跑 Node/`vite`  
   - ECS：只装镜像、跑 Python 服务，避开 npm OOM  
   这是用云 CI 而不是「在小 ECS 上 CI」的核心原因。

4. **环境分流清晰**  
   - 测试机：`push main` 或手动（`deploy.yml`）  
   - 正式机：**仅** `workflow_dispatch`（`deploy-prod.yml`），降低误推  
   GitHub 原生 concurrency / environment secrets 足够用。

5. **密钥不进镜像、不进 Git**  
   SSH 私钥、主机信息放 Actions Secrets；`.env` 留在服务器。比「本机 ssh 脚本人人一份密钥」更安全、可审计。

6. **相对 Jenkins 的成本**  
   无需常驻 Jenkins 节点、插件升级、磁盘与备份；个人/小团队量化项目，Actions 分钟数通常够用。

7. **不是银弹的地方（诚实说明）**  
   - 依赖 GitHub 可用性与国内到 GitHub 的网络  
   - 大包 SCP 到 ECS 耗时需控 exclude  
   - 复杂发布编排（蓝绿/金丝雀）要自己写脚本；当前策略是「全量替换 + 健康检查」  

**结论**：在「禁止生产热更 + 小内存 ECS + 前后端一体镜像」约束下，GitHub Actions 是性价比与可控性最均衡的选择。

## 四、Agent / AI 子系统（与业务强绑定）

### 4.1 钉钉多 Agent 编排

入口：`dingtalk_score_bot` → `dingtalk_bridge` → `coordinator`  

角色大致包括：协调者、美股/A股/加密分析师、研究、风控、执行、复盘、小管家（运维口令）等。

特点：

- **前缀/意图路由**：先规则后 LLM，控成本、稳延迟  
- **结构化输出**：分析师走 JSON，便于落库与卡片展示  
- **硬规则优先**：如 A 股 T+1、涨停禁买、跌停禁卖，不得被「风格偏好」覆盖  

### 4.2 RAG 与人类纠偏闭环

典型路径（A 股 AI 自适应 Agent）：

1. 定时扫描 → 钉钉 ActionCard（买入 / 不买入都要有理由）  
2. 用户回复卡片纠偏 → 写入 Chroma + 偏好草稿  
3. 网页「刷新并生效风格」→ 合并进提示词附言  
4. 下一轮扫描带上纠偏，但仍服从硬规则  

评分反馈、全局偏好等同理，用独立 collection 隔离。

### 4.3 小沫数字人

Web 悬浮助手：语音输入、TTS、功能导览/跳转，并可转到 Agent 能力。TTS 用 edge-tts，失败回退浏览器语音。

## 六、50 道常见 Python 开发面试题（含参考答案）

> 答题结构建议：**结论 → 原理/坑 → 项目怎么用**。以下为面试口述版参考答案。

### A. 语言与对象模型（1–12）

**1. `is` 与 `==`？小整数/字符串驻留？**  
- `==` 比值（`__eq__`）；`is` 比是否同一对象。  
- `-5~256` 小整数、部分短字符串会 intern，`is` 可能「碰巧 True」，不能当相等判断。  
- 判空：`x is None`；业务相等：`==`。

**2. 可变默认参数为什么危险？**  
- 默认值在**函数定义时**求值并复用；`def f(a=[])` 多次调用共享同一 list，造成脏数据。  
- 正确：`def f(a=None): ...; a = [] if a is None else a`。

**3. `*args` / `**kwargs` 与仅限关键字参数？**  
- `*args` 收多余位置参数，`**kwargs` 收多余关键字，便于包装与转发。  
- `def f(a, *, b)`：`b` 必须关键字传入，减少位置参数传错。

**4. 装饰器原理？`functools.wraps`？**  
- 本质是高阶函数：`f = deco(f)`，`@deco` 是语法糖。  
- 带参装饰器多一层：`@deco(x)` → `deco(x)(f)`。  
- `wraps` 保留原函数 `__name__`/`__doc__`，利于调试与 FastAPI/OpenAPI 文档。

**5. 生成器 vs 迭代器 vs 可迭代？`yield from`？**  
- 可迭代有 `__iter__`；迭代器有 `__next__`；生成器用 `yield` 实现的迭代器，惰性省内存。  
- `yield from sub` 委托子生成器，简化管道与扁平化。

**6. 浅拷贝 / 深拷贝？**  
- 浅拷贝只复制容器一层，内部可变对象仍共享引用。  
- 嵌套配置/策略参数要独立修改时用 `copy.deepcopy`；注意循环引用与性能成本。

**7. GIL 是什么？如何绕过？**  
- CPython 同一进程同一时刻只有一个线程执行 Python 字节码。  
- CPU 密集：多进程、C/Cython/numba、或换运行时。  
- IO 密集：多线程/asyncio 仍有效（等 IO 时会释放 GIL）。

**8. 线程 / 进程 / asyncio 如何选型？**  
- 共享内存的 IO 并发：线程或 asyncio。CPU：多进程。高并发网络：asyncio。  
- 混用时禁止在协程里直接跑阻塞调用；用 `asyncio.to_thread` / `run_in_executor`。本项目 LLM、Chroma 常进线程池并设超时。

**9. async 下为什么不能瞎调阻塞 IO？**  
- 阻塞会卡住整个事件循环，所有请求一起挂。  
- 把阻塞函数丢线程池，并设超时与并发上限。

**10. 上下文管理器？**  
- `__enter__`/`__exit__` 保证异常路径也释放资源（文件、锁、DB Session）。  
- `@contextmanager` + `yield` 可快速编写。

**11. 描述符与 `@property`？**  
- 描述符实现 `__get__`/`__set__`；`property` 是常用描述符，用于校验、懒加载等。ORM 字段也是类似思想。

**12. `__slots__`？**  
- 固定属性集合、省掉实例 `__dict__`、省内存；代价是灵活性下降、继承需谨慎。适合海量小对象。

### B. 数据结构与算法习惯（13–20）

**13. list / tuple / set / dict 复杂度与误用？**  
- list 下标 O(1)，中间插入 O(n)；set/dict 平均查找 O(1)。  
- 误用：用 list 做频繁 `in`；循环里反复 `+` 拼接大 list。

**14. dict 已有序，何时还要 OrderedDict？**  
- 3.7+ 保留插入序。需要 `move_to_end`、强调顺序契约、或兼容旧代码时仍可用 OrderedDict。

**15. deque / Counter / defaultdict / dataclass？**  
- 双端队列用 deque；计数用 Counter；缺省工厂用 defaultdict；结构化可变记录用 dataclass（不可变小记录可用 namedtuple）。

**16. 遍历 dict 时如何安全修改？**  
- 禁止边遍历边增删键。先 `list(d.keys())` 再改，或构建新 dict。

**17. 大文件如何避免 OOM？**  
- 按行迭代、分块 `read`；pandas 用 `chunksize`；避免一次性 `read()`/`read_csv()` 全进内存。

**18. `sort` vs `sorted`；`key`？**  
- `list.sort` 原地；`sorted` 返回新序列。优先 `key=`；复杂比较才用 `cmp_to_key`（更慢）。

**19. 时间复杂度习惯（结合 pandas）？**  
- 先估数据规模；优先向量化与布尔索引，避免 `iterrows`。先 profile 再优化，热点可上 numba。

**20. `lru_cache` 适用边界？多进程为何失效？**  
- 仅适用于纯函数、可哈希参数；注意 `maxsize` 防内存涨。  
- 多进程/多 worker 各有一份缓存，不共享；跨进程要用 Redis 等外部缓存。

### C. 并发、网络与性能（21–28）

**21. 线程安全与锁粒度？**  
- GIL ≠ 业务安全，`check-then-act` 仍竞态。共享可变状态要锁或单线程收敛。  
- 锁要细、持锁短；或改不可变 + 队列。

**22. 死锁成因与规避？**  
- 循环等待。固定加锁顺序、超时获取、减少锁、用无锁并发结构。

**23. `concurrent.futures` vs 自建线程池？**  
- futures 提供统一提交/等待/取消接口，生命周期清晰。自建池要自己管队列与关闭，一般优先标准库。

**24. HTTP 超时、重试、幂等？**  
- 必设连接/读取超时。仅对幂等请求或带幂等键的写操作重试；指数退避+抖动；限制次数，避免重试打爆下游。

**25. 连接池泄漏怎么查？**  
- 查未关闭的 Session/Response、异常路径缺少 `finally`、池打满。用上下文管理器；监控活跃连接。

**26. 性能剖析怎么用？**  
- `cProfile` 找热点函数 → `line_profiler` 看行级 → 生产用采样 profiler。先测量再优化。

**27. 引用循环、`gc`、`__del__` 坑？**  
- 循环引用靠 gc 回收；`__del__` 可能延迟或不执行，与循环共存更麻烦。优先显式 close/上下文管理器。

**28. json / orjson / pickle 取舍？**  
- 对外协议用 json/orjson。pickle 可导致任意代码执行，**禁止反序列化不可信数据**，也不利跨语言。

### D. Web / API（FastAPI 向）（29–36）

**29. WSGI vs ASGI？为何 Uvicorn/Gunicorn？**  
- WSGI 同步模型；ASGI 支持 async 与 WebSocket。FastAPI 是 ASGI，用 Uvicorn；Gunicorn+UvicornWorker 负责多进程与进程管理。

**30. `Depends` 与鉴权？**  
- 依赖注入复用「当前用户 / DB Session」等。鉴权可做成 Depends：校验 JWT，失败抛 `HTTPException`；横切逻辑也可用中间件。

**31. Pydantic 校验失败如何控错误码？**  
- 默认 422。自定义 `exception_handler`，映射成统一业务错误体（字段路径+中文提示），避免堆栈外泄。

**32. CORS？`allow_credentials` 与 `*`？**  
- 浏览器跨域安全策略。携带 Cookie 时 `Access-Control-Allow-Origin` 不能是 `*`，必须回显具体 Origin。

**33. 同步路由塞进 async 应用的危害？**  
- 框架会把 `def` 丢线程池，但池容量有限；大量阻塞仍会拖垮服务。重 CPU/阻塞 IO 要显式隔离。

**34. BackgroundTasks vs Celery/RQ？**  
- 短任务、可丢失、与请求同进程：BackgroundTasks。长任务、需重试/持久化/多机：独立队列与 worker。

**35. 幂等下单 API 怎么设计？**  
- 客户端传 `Idempotency-Key`；服务端持久化去重，相同 key 返回同一结果。订单状态机清晰（created→submitted→filled/canceled）。

**36. 限流、熔断、超时分别防什么？**  
- 限流：防刷与过载。熔断：下游持续失败时快速失败，防雪崩。超时：防无限挂起占资源。常组合使用。

### E. 数据与持久化（37–42）

**37. SQLAlchemy Session 生命周期？**  
- 常见「一请求一 Session」：边界清晰，避免跨请求脏对象。结束时 commit/rollback 并 close。

**38. N+1 如何发现与消除？**  
- 循环访问懒加载关系导致大量 SQL。用 `joinedload`/`selectinload`，或一次查询后内存组装；打开 SQL echo/慢查询观察。

**39. 事务隔离级别？交易系统关心什么？**  
- 脏读、不可重复读、幻读。资金/持仓更关心可重复读或串行化，并配合乐观锁/版本号防超卖。

**40. 索引设计？最左前缀？覆盖索引？**  
- 按高频查询建，注意选择性。联合索引遵循最左前缀。覆盖索引可避免回表。忌滥建拖慢写入。

**41. Alembic vs 生产手工改表？**  
- 迁移可审查、可复现、可回滚。手工改表造成环境漂移，最终「代码以为有列、库没有」。

**42. Cache Aside 怎么做？**  
- 读：先缓存，miss 读 DB 再回填。写：先更新 DB，再删除/更新缓存。用 TTL 接受短暂不一致。

### F. 工程、测试与质量（43–50）

**43. 虚拟环境与依赖锁定为何重要？**  
- venv 隔离项目依赖。版本钉死才能让 CI/镜像可复现；「在我机器能跑」往往是依赖漂移。

**44. 日志怎么设计？**  
- 结构化（JSON）、级别合理、带 request_id/业务单号；密钥脱敏。能量化检索「某次扫描/某订单」。

**45. 十二要素；密钥为何不进镜像？**  
- 配置外置为环境变量。密钥写进镜像层可被导出/history 挖出；应用运行时注入 Secrets/`.env`。

**46. 单测 vs 集成；如何 mock 交易所？**  
- 单测纯逻辑快速反馈；集成测 DB/HTTP。交易所 API 用 mock transport 或录制 fixture，避免测真实下单。

**47. 自定义异常 vs 业务码 vs 500？**  
- 可预期业务失败 → 4xx + 业务码。未知错误 → 500 + 日志告警。领域错误用自定义异常表达。

**48. 类型注解与 mypy/pyright 收益边界？**  
- 提升可读性与边界约束（尤其 API schema）。动态魔法过多处收益下降，要务实地标注关键路径。

**49. Docker 多阶段构建？`.dockerignore` 坑？**  
- 多阶段把编译工具留在 build 阶段，运行镜像更小更安全。  
- 本项目踩过：ignore 了 `frontend/dist`，导致 CI 预构建产物进不了镜像，运行时报缺 `index.html`。

**50. 生产事故复盘收集什么证据？**  
- 精确时间线、版本号（如 `/api/health` 的 version）、配置 diff、日志与指标、变更记录、影响面、是否已回滚。先止损再根因。

## 七、50 道 AI Agent 开发面试题（含参考答案）

> 目标：讲清「Agent ≠ 套一层 ChatCompletion」。可结合本项目：规则路由、JSON、硬规则、钉钉收评、RAG、人工确认。

### A. 基础概念与架构（1–10）

**1. 什么是 AI Agent？与 Chatbot/Copilot/Workflow 边界？**  
- Chatbot 偏对话；Copilot 偏辅助人决策；Workflow 是固定流程图。  
- Agent 能围绕目标做规划，调用工具/环境，并根据观察迭代。本项目是「编排器 + 专家分析师 + 人在环」。

**2. ReAct、Plan-and-Execute、Multi-Agent 适用场景？**  
- ReAct：探索性强、步骤不确定。Plan-Execute：步骤可先规划。Multi-Agent：角色分工（分析/风控/执行）。  
- 交易场景常用「编排 + 专家」，避免全程 ReAct 高成本高延迟。

**3. 单 Agent 工具循环 vs 多 Agent？如何防甩锅？**  
- 单 Agent 简单但提示词臃肿。多 Agent 要有清晰 I/O 契约与最终仲裁者。  
- 防甩锅：只允许协调者分派、限制互相委托次数、共享状态机。

**4. Orchestrator 应包含哪些职责？**  
- 意图路由、参数抽取、调用预算（步数/费用）、超时与熔断、审计、把结果安全地呈现给用户。

**5. 何时规则路由，何时 LLM 路由？**  
- 明确高频口令用规则：稳、便宜、可测。模糊自然语言用 LLM。  
- 本项目：前缀/关键词规则优先，LLM 兜底。

**6. Agent 状态放哪？**  
- 短会话：内存/Redis。业务真相：MySQL。风格纠偏：Chroma。工作草稿：本地 JSON。各自有 TTL 与确认策略。

**7. 同步 HTTP Agent vs 钉钉 Stream？**  
- HTTP 请求-响应，边界清晰。Stream 长连接适合群聊引用回复与主动推送，但要处理断线、超时与「有回执无正文」。

**8. Human-in-the-loop？哪些必须人工确认？**  
- 关键决策需人点头。本项目：点评先入草稿/RAG，网页确认后才改风格；真实下单更要权限与二次确认。

**9. Agent 评测有哪些层次？**  
- 工具选择准确率、任务成功率、回归集稳定性、延迟与成本；金融场景硬规则违反率必须为 0。

**10. 如何定义 Agent SLO？**  
- 例如：P95 延迟、有效正文回复率、JSON 解析成功率、违规/幻觉率、日调用成本上限。

### B. Prompt / 结构化输出（11–18）

**11. System / User 如何分工才不漂？**  
- System：角色、硬规则、输出 schema。User：当轮行情与上下文。少把易变业务细节堆进 System。

**12. 为何金融场景强制 JSON？**  
- 下游要落库、推卡片、跑硬规则校验。自然语言难稳定解析，容错成本高。

**13. 模型不吐 JSON 怎么办？**  
- 强化约束并重试；尝试修复性解析；失败则降级为 hold 并说明原因；保留原始输出便于复盘。

**14. Few-shot vs 反例清单？**  
- 反例（诱多、滞涨追涨）能直接压制错误模式，交易很管用。Few-shot 示意格式。注意控制长度与噪音。

**15. 温度等参数怎么设？**  
- 决策/工具型：低温（约 0~0.3）求稳。创意文案可略高。不要靠 penalty「拯救」烂 prompt。

**16. Prompt 注入？工具场景如何防？**  
- 用户试图让模型忽略系统规则。防护：工具白名单、硬规则代码再拦、数据与指令隔离、不把不可信文本当最高指令。

**17. 上下文不够时怎么组合？**  
- 历史摘要 + 最近 N 轮滑动窗口 + RAG 拉相关纠偏。价格与持仓仍以 API/DB 为准。

**18. Prompt 版本管理与灰度？**  
- Prompt 进 Git；纠偏走草稿确认；按群/开关灰度。禁止群里一句话直接热改生产 System。

### C. 工具调用（19–26）

**19. 工具描述差会导致什么？好 schema？**  
- 乱选工具、乱填参数。好的描述：目的一句话、参数约束、副作用、何时不该调用。

**20. 工具失败决策树？**  
- 可重试 → 有限次退避；否则换备援；再失败 → 向用户澄清或安全降级（不买入）。禁止静默失败。

**21. 如何防止死循环？**  
- `max_steps`；检测相同工具+相同参数重复；耗尽步数强制给出收束答案。

**22. 幂等工具 vs 下单如何隔离？**  
- 查询可多调。下单：独立权限/开关/幂等键，默认只给「建议」不自动成交（本项目一期信号路线）。

**23. 并行工具调用的收益与风险？**  
- 加速无依赖查询；有写入依赖或共享状态时并行可能不一致，需串行化关键写路径。

**24. 查库/行情工具的超时与缓存？**  
- 短超时；TTL 缓存；过期可返回 stale 并标记。阻塞 IO 放线程池，避免卡住会话循环。

**25. 如何记录 thought/tool/obs？**  
- 每步结构化日志：工具名、参数摘要、耗时、成败。密钥与完整行情大包要脱敏/截断。

**26. 工具结果过大怎么截断？**  
- 保留统计摘要与决策关键字段；全文落盘，模型按需再取片段，避免上下文爆掉。

### D. RAG 与记忆（27–36）

**27. RAG 解决什么、不解决什么？**  
- 解决：注入历史纠偏与风格偏好。不解决：实时行情、成交真相、合规硬约束——必须代码与数据源。

**28. 分块策略怎么选？**  
- 纠偏适合「一条纠偏一条文档」。长研报按标题/语义切。统一写入 metadata（标的、时间、来源）。

**29. Embedding 选型与降级？**  
- 质量优先专用 embedding。无 GPU/难下载 ONNX 时可 hash 嵌入保服务可用（召回变差但不死机）。

**30. top-k、阈值、metadata 过滤？**  
- top-k 控数量；分数阈值滤噪声；metadata 按 code/周期/来源过滤，避免串票。

**31. 如何避免过期纠偏污染？**  
- 时间衰减、过期归档、**人工确认门**；未确认草稿不进 System Prompt。

**32. 短期 / 长期 / 工作记忆？**  
- 短期：当前会话。长期：Chroma 偏好。工作记忆：本轮 bars/基本面，用完即弃。

**33. 偏好如何避免覆盖硬规则？**  
- Prompt 写明优先级；代码侧 `apply_hard_rules` 后置强制；冲突时以 T+1/涨跌停等为准。

**34. 如何评估 RAG？**  
- 标注集上测召回/精确；检查答案是否 grounded；对交易敏感语句做人工抽检。

**35. 为何多 collection 隔离？**  
- 评分反馈、全局风格、A 股纠偏语义不同；隔离防检索串味，也便于权限与清理。

**36. 用户要求删除记忆怎么做？**  
- 按 id 删除向量与草稿条目并审计；无法从已发出的历史消息中「收回」，但可停止未来使用。

### E. 多 Agent、安全与交易场景（37–44）

**37. 分析师与风控冲突以谁为准？**  
- 风控/硬规则一票否决。实现上先出分析再过风控函数，或显式优先级表。

**38. 「建议」与「真实下单」权限边界？**  
- 建议：只读数据+推送。下单：独立密钥、开关、审批。审计所有写操作。一期可只做信号。

**39. 幻觉导致错信号的产品护栏？**  
- 结构化输出、硬规则、数据不足强制 hold、必须写 thesis、风格变更需人工确认。

**40. 评分配方与 LLM 不一致怎么仲裁？**  
- 同时展示两边；低置信度标记人工复核；硬规则优先；记录 divergence 用于调参。

**41. 群聊如何识别「回复某张卡片」？**  
- 解析引用 `repliedMsg`；卡片含稳定 marker；服务端 `remember_last_signal_context` 回落。

**42. 成本控制手段？**  
- 规则挡掉简单意图；短时缓存；小模型路由；限制扫描频率；只在决策节点调大模型。

**43. 密钥、Webhook、staff_id 如何防冒用？**  
- 签名校验、Secrets 管理、身份绑定、防重放；群回复不回显密钥。

**44. 合规与审计要留哪些字段？**  
- 免责声明；谁在何时对何标的给出何 action；模型/提示词版本；输入摘要；是否经人工确认。

### F. 工程落地与排障（45–50）

**45. 「只回收到、不回正文」常见根因？**  
- LLM/向量库超时、容器 OOM(137)、事件循环被阻塞、异常被吞只 ACK。应查日志、内存、超时与线程池。

**46. 如何隔离 LLM 调用避免拖垮主循环？**  
- 丢线程池 + Future 超时；超时返回降级话术；限制池大小与排队长度。

**47. 容器内存墙下如何取舍？**  
- worker=1；embedding 可降级；限制并发；拆分 api 与 dingtalk-agent 的内存配额（本项目 agent 更高）。

**48. 端到端回归怎么做？**  
- 固定行情 fixture + 固定纠偏文本；断言 action、硬规则、是否入库；Prompt 变更必跑。

**49. 灰度发布怎么做？**  
- 功能开关、群白名单、用户白名单；先测试机后正式；保留镜像版本以便 rollback。

**50. 结合本项目讲一个闭环与失败模式？**  
- **闭环**：扫描 → 钉钉 ActionCard（含不买入理由）→ Stream 纠偏 → RAG/草稿 → 人工「刷新并生效」→ 下轮 `_prefs_block`。  
- **失败模式**：未确认就当生效；偏好试图覆盖涨停规则；ECS 上 npm OOM；`.dockerignore` 丢掉 dist；无版本无法回滚。  
- **对策**：确认门、硬规则代码化、CI 预构建前端、保留 dist、发布版本标签与回滚。

回答 Python 题时可贴的真实点：
