## 一、基础概念

### 1. 深拷贝和浅拷贝的区别

| 方式 | 说明 |
|------|------|
| 浅拷贝 | 只复制最外层对象，内部嵌套元素依旧共享引用 |
| 深拷贝 | 递归复制所有层级对象，完全独立 |

**常用 API：** `copy.copy()`（浅拷贝）、`copy.deepcopy()`（深拷贝）。

---

### 2. `*args` 和 `**kwargs` 的作用

| 语法 | 作用 |
|------|------|
| `*args` | 接收任意数量的位置参数，保存为元组 |
| `**kwargs` | 接收任意数量的关键字参数，保存为字典 |

**典型场景：** 编写通用装饰器、封装第三方 API、路由函数转发参数。

---

### 3. 装饰器

装饰器本质是函数，利用闭包实现，用于在不修改原函数代码的情况下增强其功能（如日志、鉴权、计时、重试）。

```python
def log_call(func):
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@log_call
def add(a, b):
    return a + b
```

---

### 4. Python 垃圾回收机制

Python 主要依赖以下机制协同工作：

1. **引用计数**（主要机制）：对象引用数归零时立即回收
2. **标记-清除**（补充）：处理容器对象间的循环引用
3. **分代回收**（优化）：按对象存活时间分代，减少全量扫描开销

---

### 5. 列表推导式和生成器表达式的区别

| 对比项 | 列表推导式 | 生成器表达式 |
|--------|------------|--------------|
| 语法 | `[x for x in iterable]` | `(x for x in iterable)` |
| 求值方式 | 立即生成完整列表 | 惰性求值，按需生成 |
| 内存占用 | 较高 | 极低 |

**选择建议：** 数据量不大时用列表推导式；数据量大且按需消费时用生成器表达式。

## 二、并发、性能与框架

### 1. 多线程、多进程、异步 I/O 的区别与选择

| 模型 | 适用场景 | 特点 |
|------|----------|------|
| 多线程 | I/O 密集型 | 同一进程共享内存；CPython 受 GIL 约束，CPU 并行能力有限 |
| 多进程 | CPU 密集型 | 每个进程独立 GIL，可利用多核 CPU |
| 异步 I/O | 高并发 I/O 密集型 | 单线程事件循环 + 非阻塞 I/O，协程切换开销小 |

#### 本项目应用场景

本项目**主要使用多线程 + asyncio 协程**，典型场景包括：

- AI 信号评分（DeepSeek HTTP、钉钉推送）
- 实盘策略运行（每策略独立线程 + 独立事件循环）
- 监控轮询（金十快讯、币安、Polymarket、链上活动等）
- K 线后台同步、研究卡片价格定时刷新

上述任务均为**阻塞型 I/O**（等网络响应），设计目标是「接口快返回、任务慢慢跑」。

#### 本项目并发模型（面试可答）

> 「FastAPI 单进程事件循环 + 守护线程 + 策略线程内独立 asyncio」的混合并发模型。

| 层次 | 实现方式 |
|------|----------|
| API 层 | FastAPI + uvicorn 单 worker |
| 定时调度 | `asyncio.create_task` 启动 K 线同步、盯市、上涨扫描等循环 |
| 阻塞任务隔离 | `asyncio.to_thread()` 将同步重活丢到线程池，不阻塞事件循环 |
| 长驻后台 | `threading.Thread(daemon=True)` 跑监控、评分、扫描 |
| 策略执行 | 每策略一线程，`asyncio.new_event_loop()` + `run_until_complete(strategy.run())` |
| 跨线程投递 | Webhook 用 `asyncio.run_coroutine_threadsafe()` 向策略线程投递信号 |

**并发量级：** 面向个人/小团队量化场景，并发量低；通过锁、防抖、任务互斥和后台化保证稳定性，而非通过多进程/消息队列追求高吞吐。

**未使用：** `multiprocessing`、Redis 任务队列、uvicorn 多 worker 水平扩展。

#### 系统按 IO 类型拆分（口述版）

Webhook 接收、交易所 REST 拉取、LLM 调用都是 IO 密集 → 用协程；pandas 计算、CSV 解析等阻塞活不放事件循环里，用 `asyncio.to_thread` 丢到线程池。整体是**线程 + 协程**。

#### 异步和同步怎么选

| 场景 | 选择 |
|------|------|
| 行情抓取、调大模型、等 HTTP | 异步或线程，避免一个慢请求堵住整个进程 |
| 改账户、下单、写同一条状态 | 控制并发，不能两个请求同时改同一实例 |
| 页面查询 | 普通同步接口即可 |

#### Python 异步和多线程互斥

- 协程里用 `asyncio.Lock`
- 多线程里用 `threading.Lock`
- 因为有 GIL，同一时刻只有一个线程在执行字节码，多线程跑 CPU 活快不了，所以更多用协程做 IO 并发

### 2. 协程

协程是一种轻量级的异步编程方式，可在单线程内通过协作式切换实现多个任务的并发执行（非并行）。

**本项目中的协程使用点：**

| 模块 | 用途 |
|------|------|
| `api/main.py` | 定时任务循环（`_kline_sync_loop`、`_daily_a_share_mtm_loop` 等） |
| `strategy/*.py` | 策略 `run()` 内 `await` 行情、下单、`asyncio.sleep` 轮询 |
| `engine/webhook_trading.py` | `aiohttp` 异步 HTTP |
| `core/api_client.py` | 对外 `async def`，内部 `asyncio.to_thread` 包装同步 `requests` |
| `dingtalk_score_bot.py` | dingtalk-stream SDK 要求的 `async def process` 入口 |

---

### 3. GIL 机制

**GIL（Global Interpreter Lock）** 是 CPython 解释器的全局互斥锁，保证同一时刻只有一个线程在执行 Python 字节码。

#### GIL 与 `threading.Lock` 的区别

| | GIL | `threading.Lock` |
|---|-----|------------------|
| 管理者 | 解释器自动管理 | 程序员手动加锁 |
| 保护范围 | Python 字节码执行 | 业务共享数据（dict、JSON 文件、缓存状态） |
| 能否替代 | — | GIL **不能**替代 Lock，两者职责不同 |

#### 为什么 IO 密集多线程依然有效

IO 操作（网络请求、文件读写、数据库查询）在底层会释放 GIL。当线程 A 发起请求阻塞时，会主动释放 GIL，线程 B 就能拿到 GIL 继续执行，所以多线程在 IO 密集场景下能实现并发，有效提升吞吐量。

#### GIL 何时影响小

线程在等待网络 I/O、`time.sleep()`、部分 C 扩展计算时会释放 GIL，因此本项目大量 I/O 密集线程（评分、监控、同步）**不受 GIL 明显拖累**。

#### 本项目应对措施

| 措施 | 文件示例 | 作用 |
|------|----------|------|
| `threading.Lock` | `dingtalk_signal_cache.py` | 保护最近信号 JSON 缓存 |
| `threading.Lock` | `crypto_signal_scorer.py` | 保护评分缓存与历史记录 |
| `threading.Lock` | `crypto_signal_hub.py` | 扫描任务互斥（`_scan_lock`） |
| `threading.Lock` | `strategy.py` | K 线后台同步防抖（`_bg_sync_lock`） |
| 守护线程 + 快速返回 | `dingtalk_score_bot.py` | 评分不阻塞钉钉回调 |
| 未用多进程 | — | 瓶颈在外部 API 延迟，非本地 CPU |

**面试一句话：** 本项目运行在 CPython GIL 之下，用多线程做 I/O 并发；对共享缓存和任务状态用 `threading.Lock` 保证线程安全；CPU 密集部分未用多进程绕开 GIL，因为当前瓶颈主要在网络延迟。

#### 你在系统中分别用了什么并发模型

| 场景 | 模型 | 原因 |
|------|------|------|
| 行情拉取 | 协程 | 对接 Binance/OKX 等多交易所 WebSocket/REST，单线程内处理多连接，开销小于线程 |
| 策略回测 | 多进程 | 大量 pandas/指标计算需绕开 GIL，用多核；不同策略/标的拆独立进程，`Pool.map` 分发 |

#### GIL 与异步（Webhook + 多交易所 + LLM）

系统按 IO 类型拆分：Webhook 接收、交易所 REST、LLM 调用都是 IO 密集 → 协程；pandas/CSV 等阻塞不放事件循环，用 `asyncio.to_thread`。主要是**线程 + 协程**。

### 4. FastAPI / Docker / 接口设计

#### 量化系统为什么用 FastAPI

接口多，要接 Webhook 和异步任务；FastAPI 写接口快，参数和返回结构清楚，能快速出原型。

#### Docker 在项目中解决什么问题

把 Python 服务、依赖和运行环境打进镜像；量化系统用容器跑 API，前面用 Nginx 转发。

#### 接口怎么设计才好联调

- 路径表明资源，例如实例的启动、停止、修改参数分开
- 返回里有明确成功或失败原因
- 入参先校验类型和范围：杠杆、止盈止损百分比不合法就拒绝

#### 幂等是什么，你哪里用了

同一次请求执行多次，结果与执行一次一样。TradingView 可能重推，钉钉通知也可能失败重试，所以用信号 ID 或内容摘要做去重，数据库再建唯一索引兜底；已处理过的不再下单、不再推一次。

#### 安全性

- HMAC 签名校验：TradingView 用密钥对 payload 签名，服务端用同样密钥验签，防止伪造
- IP 白名单、HTTPS

---

### 5. 一条信号从进来到通知的路径

TradingView 消息推送到 Webhook → 服务解析品种、方向、策略 ID → 按映射推到对应钉钉群；同时根据信号时间戳从交易所取对应时段 K 线，计算 MACD、RSI 等指标后调用 DeepSeek 做信号评分。

## 三、LLM 与 Agent

### 1. LLM 和 Agent 的区别

| | LLM | Agent |
|---|-----|-------|
| 本质 | 输入文本 → 输出文本 | 在 LLM 外包一层「循环 + 工具 + 状态」 |
| 记忆 | 无（每次调用无状态） | 有短期/长期记忆 |
| 行为 | 不会主动做事 | 自主决策、调工具、目标导向 |

**一句话：** `Agent = LLM + 工具 + 记忆 + 循环`

---

### 2. Agent 与 Workflow 的区别

| | Agent | Workflow |
|---|-------|----------|
| 决策 | 模型自主决定方向 | 按预先设定步骤执行 |
| 过程 | 观察 → 行动 → 学习 | LLM 按固定流水线走 |

**生产环境怎么选：**

- 流程固定 → Workflow
- 需要根据上一步结果设计下一步 → Agent
- 也可 Workflow + 局部 Agent

---

### 3. Agent 的核心组成模块

`Agent = Profile + Memory + Planning + Action`

| 模块 | 含义 |
|------|------|
| Profile | 角色设定 → 对应 system prompt |
| Planning | 规划 / reflection，决定 Agent 能力上限 |
| Memory | 短期（上下文）+ 长期（RAG） |
| Action | 工具调用、Skill、外部世界交互（MCP），结果反馈进循环 |

**生产最容易出问题：**

- Memory 管理：短期关键内容没保存；长期知识召回不准
- Tool calling：调用失败、参数错误

---

### 4. Agent Runtime 是什么

Agent 的决策逻辑 vs Agent Runtime（执行引擎）：

| 能力 | 说明 |
|------|------|
| 状态管理与持久化 | 支持中断后从 checkpoint 恢复，而不是从头跑 |
| 工具执行与沙箱化 | 隔离环境 |
| 并发与调度 | 多工具并行、多 Agent 协作时的限流与资源分配 |
| 错误处理与重试 | 可观测性、上下文与资源管理 |

**区别：**

- Agent 负责决策：下一个调什么工具、任务是否完成
- Agent Runtime 关注怎么执行

### 5. Function Calling

流程：注册工具 → 模型决策 → 宿主系统拦截并执行 → 结果回填。

结构化约束输出（JSON Schema 等）。

### 6. MCP（Model Context Protocol）

定义 AI 模型 / Agent 如何以标准化方式连接外部工具、数据源和服务。

**解决的问题：** M×N 集成问题（M 个 Agent、N 个工具需要 M×N 套定制适配）→ MCP 变成 **M+N**。

| 角色 | 说明 |
|------|------|
| MCP Server | 工具/数据提供方，暴露工具、资源、prompt 模板 |
| MCP Client | 内嵌在 Agent 应用里，负责发现可用 Server |

**MCP 与 Function Calling：**

- Function Calling：模型层面表达「要调用工具」的能力
- MCP：更上层协议，解决工具如何被标准化接入和管理

---

### 7. Agent Skills

文件夹形态：`name`（描述运用场景）+ `description`（模型看的操作指南）；命中 name 后加载 description。

- Skills：告诉 Agent **怎么做**（流程化知识）
- MCP：负责 **能不能** 连到外部系统

---

### 8. Agent Memory

解决模型没有记忆。

| 层次 | 存放 | 用途 |
|------|------|------|
| 感觉记忆 | — | 瞬时感知 |
| 短期记忆 | 内存 | 最近几轮对话 |
| 长期记忆 | 向量库 | 用户画像、偏好、历史重要事件，RAG 按需召回 |
| 工作记忆 | Redis | 当前任务状态 |

**RAG vs Memory：**

- RAG：外部知识库
- Memory：记自己的经历和状态

**本项目 RAG 检索：** 混合检索（相似度 + 关键词）+ 时间衰减（越近权重越高）。

### 9. 常见 Agent 范式

| 范式 | 要点 | 适用 |
|------|------|------|
| ReAct | 想一步、做一步、看结果、再想 | 任务边界清晰、单步操作居多 |
| Plan-and-Execute | 全局规划，拆解子任务 | 步骤间有明确依赖的复杂任务 |
| Reflection | 反思复盘 | 与上两者组合：Plan 分解 + ReAct 循环 + Reflection 复盘 |

---

### 10. Subagent 与 Multi-agent

**Multi-agent：** 多个 Agent 协同完成复杂任务。任务越复杂，上下文越多，专注度下降。

**Peer Collaboration：** 对等协作，共享消息总线，通信关系按 O(n²) 扩展，Agent 一多协调易失控。

**Subagent：** 由主 Agent 按需派发的临时、隔离执行单元，彼此没有点对点通道。

**是一回事吗？** Multi-agent 是更宽泛的多 Agent 协作概念；Subagent 是 orchestrator 架构下派生出的隔离执行单元。

### 11. Agent Evaluation

| 对比 | 普通 LLM | Agent |
|------|----------|-------|
| 评什么 | 一次输入对一次输出 | 多步执行（错误会复合累计） |
| 确定性 | 相对固定 | 同样输入可能走出不同路径 |
| 成功标准 | 答案对错 | 开放式，步骤不同≠结果错 |

**关注指标：** Task Success Rate、工具调用正确性、恢复质量、安全性、单位成本。

**怎么设计评估体系：**

- 离线：标准任务集 + 跑分器做基准
- 线上：真实执行轨迹监控
- 把 Agent 评估当成持续回归测试

### 12. Context Engineering

原因：LLM 处理长上下文表现会下降。

| 失败方式 | 对策 |
|----------|------|
| Poisoning 污染 | Write：外部化存储，需要时取回 |
| Distraction 分心 | 精确检索（对应 RAG） |
| Confusion 混乱 | 压缩：摘要/精简，省 token |
| Clash 冲突 | 隔离：不同类型 context 分开管理 |

**与 Harness 的关系：**

- Harness：让 Agent 能安全、可恢复地运行（沙箱、审批、生命周期）
- Context Engineering：决定模型每一轮看到什么的运行时纪律，是 Harness 核心能力之一

### 13. Harness 工程

**比喻：**

- Model：很聪明但被关在小黑屋的实习生——会思考说话，但没有手、脚、记忆、权限
- Harness：公司给实习生配的整套办公室——工具、规章、秘书、门禁、项目经理，让他能安全干活

| Harness 组件 | 对应 |
|--------------|------|
| System Prompt | 员工手册：角色、边界、目标 |
| Tools / Skills / MCP | 工具箱 |
| Filesystem + Sandbox | 隔离工位 |
| Browser | 网页与真实世界验证 |
| Orchestration | 项目经理：Subagent 派生、交接、路由 |
| Hooks / Middleware | 门禁：压缩、续跑、lint 等确定性执行 |

| | Model | Harness |
|---|-------|---------|
| 能力 | 输入文本/图像/音频/视频 → 输出文本 | 跨会话持久状态、代码执行、实时知识、环境与依赖 |

### 15. 评测数据集构建

1. **线上真实日志：** 抽取用户真实 query，随机抽样并人工标记（冷启动：业务场景推演 → 与产品头脑风暴穷举说法 → 构成评测集）

3. **大模型合成**

**动态迭代：** bad case 回流，线上识别错误脱敏后加入评测集。评测集关键：**覆盖率**，覆盖多个应用场景。

### 16. 什么样的 Prompt 效果好

`Prompt = 角色 + 任务 + 上下文 + 约束 + 样例`

角色清晰、任务简洁具体、约束严格、格式固定，给定几个覆盖广、代表性强的 few-shot 示例。

### 17. Vibe Coding 如何保障交付质量

任务拆碎 → 先 review、对问题扩写 → 生成 planning 交人工审核 → 审核后执行 → 执行后测试 → 运行结果再交给 Agent。

### 18. RAG 完整链路

文档解析 → 文档切片 → 向量化存入向量库  

用户 query → query 向量化 → 相似度召回 → 重排 → 按 prompt 拼上下文 → 大模型生成答案

**本项目切分：** 基于 Markdown 结构的语义切分。

**冲突管理：**

- 元数据加时间标签，时间倒序
- 或引入重排序（如 BGE-reranker），时效强、相关性高的排前面
- 冲突严重：强制 LLM 输出警告，人工确认后再处理

### 20. 为什么不使用 LangChain / LangGraph

- **不用 LangChain**（适合快速拼工具链）：模型调用是薄封装，记忆和工具是领域逻辑，直连 API 更可控
- **不用 LangGraph**（适合复杂状态机）：协作是确定性路由，不是复杂状态图

## 四、数据库与缓存

### 1. Redis 缓存穿透、击穿、雪崩怎么防

| 问题 | 含义 | 防护 |
|------|------|------|
| 穿透 | 查不存在的数据 | 布隆过滤器拦截 + 空值缓存 |
| 击穿 | 热点 key 过期 | 互斥锁 |
| 雪崩 | 大量 key 同时过期 | 过期时间随机抖动 |

量化后台行情：本地缓存（LRU）+ Redis 二级缓存，降低 Redis 压力。

---

### 2. 慢查询定位、Extra 含义

开慢查询日志。

| Extra | 含义 | 优化 |
|-------|------|------|
| Using filesort | 排序没走索引 / 额外排序 | 加合适联合索引，让 ORDER BY 跟上索引顺序 |
| Using temporary | 用了临时表 | 改查询语句 |
| Using index | 索引覆盖/下推，减少回表 | 覆盖索引优化 |

---

### 3. 连接池怎么配，打满会怎么样

按 CPU 核数×2 + 磁盘数，结合压测定。打满请求超时；太小排队。项目中按 QPS 和单查询消耗估算，配最大连接 + 等待超时 + 监控。

---

### 4. 死锁产生、排查、减少

互相持有对方需要的锁。`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`。

**减少：** 统一加锁顺序、缩短事务、走索引减少锁范围、避免大事务。

---

### 5. 深分页与多条件分页、Explain、分库分表

深分页慢是因为 `LIMIT N,M` 要扫描丢弃前 N 行。

**优化：**

1. 延迟关联（先用覆盖索引取主键再 JOIN 回表）
2. 游标 / seek 分页（`id > last_id` 或 `trade_time < last_time`）
3. 限制最大可翻页数

多条件查询：等值列在前、范围列在后建联合索引，如 `(symbol, status, created_at)`，让时间范围走索引最后一列。

### Pandas 内存打爆

1. 看 OOM 位置，用 `tracemalloc` 或 `memory_profiler` 定位峰值
2. 优化：只读必要列；指定 dtype；分块读（`chunksize`）或按时间窗口流式处理；计算指标避免全量复制，用向量化 + 原地处理
