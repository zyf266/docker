# 第二部分：Python 基础与并发（简历「专业技能 1」）

### Q6. 说说 GIL，为什么你还用多线程？
**答：**  
GIL 保证同一时刻只有一个线程执行 Python 字节码，所以纯 CPU 计算多线程加速有限。但我大量工作是网络 IO（交易所、LLM、钉钉），阻塞等待时会释放 GIL，其他线程可继续跑，吞吐量能上来。CPU 重活（回测、大批量 pandas）才考虑多进程绕开 GIL。

### Q7. 多线程、多进程、协程怎么选？你项目怎么用？
**答：**  

| 模型 | 适用 | 我怎么用 |
|------|------|----------|
| 协程 asyncio | 高并发 IO | FastAPI 定时任务、策略 await 下单、Webhook 异步 |
| 多线程 | 阻塞 IO / 与同步库共存 | 监控轮询、评分后台、`to_thread` 包 requests |
| 多进程 | CPU 密集 | 回测/重计算场景（简历声明会选型落地） |

量化后台是「FastAPI 事件循环 + 守护线程 + 策略线程内独立事件循环」的混合模型：接口快返回，重活后台跑。

### Q8. `threading.Lock` 和 GIL 区别？
**答：**  
GIL 保护解释器字节码执行；`Lock` 保护业务共享状态（缓存 dict、JSON 文件、扫描任务互斥）。GIL 不能替代 Lock，多线程改同一缓存仍要加锁。

### Q9. 列表推导 vs 生成器？pandas 大数据怎么防 OOM？
**答：**  
列表推导立即占内存；生成器惰性按需产出。pandas：只读必要列、指定 dtype、`chunksize` 分块、避免无意义 copy、向量化计算；用 tracemalloc 定位峰值。

### Q10. 深拷贝浅拷贝、装饰器、`*args/**kwargs`（快问）
**答：**  
浅拷贝只拷外层引用；深拷贝递归独立。装饰器闭包增强函数（鉴权、重试、日志）。`*args` 元组收位置参数，`**kwargs` 字典收关键字，常用于转发与通用封装。

# 第三部分：全栈后端 FastAPI / DRF（简历技能 3 + 工作/项目）

### Q11. 为什么量化用 FastAPI 而不是 Django？
**答：**  
接口多、要接 Webhook 和异步任务；FastAPI 基于类型注解和 Pydantic，参数校验与 OpenAPI 生成快，异步友好。Django/DRF 适合偏后台 CMS；邦业考试系统我用过 DRF+Vue3，说明两种都能做，按场景选型。

### Q12. RESTful 怎么设计才好联调？
**答：**  
资源路径清晰（实例启动/停止/改参分开）；统一返回 `ok` + `detail`；入参先校验范围（杠杆、止盈止损百分比非法直接 400）；错误可定位。Portal 的 watchlist、exchange、tv-webhook 都按资源拆路由。

### Q13. 同步接口里怎么跑阻塞 HTTP 不卡死事件循环？
**答：**  
用 `asyncio.to_thread()` 或线程池把 `requests` 丢出去；或改 aiohttp。Webhook 交易路径还要避免和 LLM 评分抢同一条慢链路，所以评分旁路、进程拆分。

### Q14. 鉴权怎么做？Portal 和管理端如何分流？
**答：**  
JWT Bearer；角色区分管理端与普通用户 Portal。未登录跳登录；管理 API 可再加 admin 校验。密钥类数据不进前端明文。

### Q15. DRF+Vue3 你做了哪些性能优化？（邦业/天山考试系统）
**答：**  
后端：接口字段裁剪、必要缓存、索引与分页；前端：组件化、减少无效渲染、资源压缩/CDN；用压测模拟高 QPS 找瓶颈，全链路调优。分库分表/缓存是复杂数据场景的设计能力表述——面试要能举「什么表、按什么键分、缓存什么、失效策略」。

### Q16. 前后端分离职责怎么拆？
**答：**  
后端管鉴权、业务规则、数据一致性；前端管交互与展示。约定接口契约（字段、错误码），用组件库统一交互，降低维护成本。

# 第五部分：Webhook、交易与交易所对接（沐龙核心）

### Q21. 讲一条 TradingView 信号到下单的完整路径
**答：**  
TV POST → `/api/portal/tv-webhook` → 解析 strategy_name/symbol/timeframe/signal → 匹配 `status=connected` 的观察库配置 → 解密用户绑定的交易所密钥 → 按仓位模式算保证金 → 市价开仓 → 按止盈止损百分比挂 TP/SL；同向已有仓跳过。另有 dry-run 只演练不下单。

### Q22. 为什么要策略名+币种+周期三元组匹配？
**答：**  
同一用户可能多策略多周期；三元组精确定位配置，避免误跟单。多用户同名策略会都执行——本地/单租户可接受，生产可加 webhook token 防撞名。

### Q23. 幂等怎么做？TV 重推怎么办？
**答：**  
信号 ID 或内容摘要去重；库表唯一索引兜底；已处理不再下单/不再重复推钉钉。限流与失败降级保证主 API 不被拖死。

### Q24. Webhook 安全？
**答：**  
HMAC 验签、HTTPS、必要时 IP 白名单；Portal webhook 当前偏内网/演示，正式环境应加强鉴权与审计日志。密钥 RSA 加密落库，日志只打 mask。

### Q25. 对接 Binance/OKX/Hyperliquid 难点？
**答：**  
协议差异（REST/WS、签名、合约面值）；限流与重试；HL 用私钥钱包，OKX 用 Key/Secret/Passphrase；统一在业务层做「绑定-验资-下单-持仓」抽象。余额为 0 时开仓前要拦截。

### Q26. 多进程拆分 API / Webhook / Agent 的原因？
**答：**  
交易要低延迟，不能和重 LLM、长轮询抢资源和重启窗口；拆进程后可独立扩缩与发布，故障隔离。

# 第六部分：Portal、缓存、安全（简历工作 4、6）

### Q27. 交易所密钥如何存储？
**答：**  
RSA 加密后入库（`*_enc` 字段）；接口回显只给 mask；解密仅服务端下单/验资时使用。禁止写进前端或日志明文。

### Q28. 观察库指标为何 30 分钟缓存？用什么存？
**答：**  
K 线拉取贵且易超时；内存 + 磁盘 JSON 缓存，TTL 30 分钟；进页默认读缓存，force 才重拉。用磁盘是为了 API 重启不丢、实现简单；更高并发可上 Redis 二级缓存。

### Q29. Redis 穿透/击穿/雪崩？（简历提到 Redis）
**答：**  

| 问题 | 防法 |
|------|------|
| 穿透 | 布隆 + 空值短缓存 |
| 击穿 | 互斥锁重建 |
| 雪崩 | 过期时间加随机抖动 |

商城用 MySQL+Redis+Chroma；量化热点可用本地 LRU + Redis。

### Q30. 禁止生产热更是什么规范？
**答：**  
正式环境禁止 docker cp/手改代码；唯一路径本地改 → push → GitHub Actions 全量部署，保证可追溯可回滚，降低人为事故。

# 第七部分：Agent / LLM / RAG（简历优势 + 技能 4 + 项目）

### Q31. LLM 和 Agent 区别？
**答：**  
LLM：文本进文本出，无状态。Agent：LLM + 工具 + 记忆 + 循环，能决策、调工具、为目标服务。  
`Agent = LLM + Tools + Memory + Loop`。

### Q32. 你的多 Agent 怎么编排？
**答：**  
意图路由后分角色：分析师/风控/执行/复盘/小管家；Webhook 信号进评分卡片，统一钉钉触达。协作偏确定性路由，不是盲目对等群聊，避免 O(n²) 失控。

### Q33. Agent vs Workflow？生产怎么选？
**答：**  
流程固定用 Workflow；要据上一步动态规划用 Agent；也可 Workflow 主流程 + 局部 Agent。量化评分推送偏固定链路，复杂问答/商城助手偏 Agent。

### Q34. Function Calling 流程？敏感操作为何要确认？
**答：**  
注册工具 → 模型选型调用 → 宿主执行 → 结果回填。商城里下单/支付/退款用 `confirm_token` + 用户确认落库，禁止模型自动改资金，控幻觉与误操作风险。

### Q35. RAG 完整链路？你怎么切分与解决冲突？
**答：**  
解析 → 切片 → 向量化入库；Query 向量化 → 召回 → 重排 → 拼 Prompt → 生成。切分可用 Markdown 语义切分。冲突：时间元数据倒序、Reranker、严重时输出警告人工确认。

### Q36. Memory 怎么分层？
**答：**  
短期：最近对话（内存）；长期：向量库画像/偏好/事件（RAG 召回）；工作记忆：任务状态（可用 Redis）。检索可混合相似度+关键词+时间衰减。

### Q37. 为何简历写会 LangChain/LangGraph，项目里又强调可控？
**答：**  
框架能加速原型；核心业务（交易、确认落库、钉钉路由）需要强约束，直连 API 更可控。面试态度：会用框架，但不为用而用，按复杂度选型。

### Q38. MCP 和 Skills 是什么？
**答：**  
MCP：标准化连接工具/数据，解决 M×N 适配。Skills：流程化操作指南（怎么做）；MCP 管连不连得上。与 ACP/训练师认证知识体系统一口述。

### Q39. Prompt 怎么写才稳？结构化输出？
**答：**  
角色+任务+上下文+约束+样例；强制 JSON/字段校验，评分结果可解析入库与推送。

### Q40. ASR/TTS 语音助手怎么做？
**答：**  
Web 语音识别 + TTS（如 edge-tts）挂在量化后台浮窗；与 FastAPI 对话接口打通，注意浏览器权限与延迟。

### Q41. Vibe Coding / Context 工程你怎么保证质量？
**答：**  
任务拆碎 → 扩写需求 → planning 人工审 → 再实现 → 跑通验证 → 结果回喂。Context 控制污染/分心/混乱/冲突（外置存储、精检索、压缩、隔离）。Harness 管沙箱、工具、门禁与可恢复执行。

### Q42. 智能商城 Agent 技术亮点（深挖）
**答：**  
DeepSeek Tool Calling（接单、推荐、比价、物流、售后）；确认落库；Qwen-VL 以图搜品；行为→画像→向量召回个性化；2c2g ECS + Docker/Nginx 同源部署；支付物流 Mock 保证可演示。

# 第八部分：数据库 MySQL（技能 5 + 同花顺/邦业）

### Q43. 索引原则？联合索引顺序？
**答：**  
高选择性、最左前缀；等值列在前、范围列在后，如 `(symbol, status, created_at)`。用 Explain 看是否 Using filesort/temporary。

### Q44. 慢查询怎么查？Extra 常见项？
**答：**  
开慢查询日志。Using filesort→优化 ORDER BY 与索引；Using temporary→改写 SQL；Using index→覆盖索引减少回表。

### Q45. 深分页优化？
**答：**  
`LIMIT N,M` 丢弃前 N 行成本高 → 延迟关联、seek/游标分页（`id > last_id`）、限制最大页。

### Q46. 事务与死锁？
**答：**  
死锁是循环等待锁。`SHOW ENGINE INNODB STATUS` 看最近死锁。减少：统一加锁顺序、短事务、走索引缩小锁范围。

### Q47. 连接池打满？
**答：**  
按核数与压测定 max connections；打满超时，过小排队。配等待超时与监控。

### Q48. 分库分表你会怎么做？（简历提到）
**答：**  
先垂直按域拆；水平按用户/标的/时间分片；中间件或应用路由；注意跨片事务与分页。量化配置表未必需要上分片，先索引与缓存，真热点再拆——体现「不过度设计」。

# 第十部分：数据处理 Pandas（技能 2、同花顺财报、硬件清洗）

### Q52. 财报清洗难点？
**答：**  
多周期报表结构差异；正则与 SQL 结合批量清洗去重标准化；异常指标体系监控营收利润资产负债，企微/邮件触达。

### Q53. 粗清洗 vs 细清洗？
**答：**  
粗清洗：统一入口、类型、明显脏数据；细清洗：配置文件规则引擎处理缺字段、格式异常，便于业务改规则不改代码。

### Q54. 数据一致性校验怎么做？
**答：**  
字段级/维度级/汇总级比对自动结果与源财报，定位差异推动修正，保证全链路可靠。

# 第十一部分：Docker / Linux / CI-CD / Nginx（技能 6、7）

> 口述主线（沐龙量化）：本地/测试 Compose 起多容器 → Actions 构建前端+镜像包 → SSH 到 ECS 安装重启 → Nginx 反代 8100 → 正式机禁止热更、可版本回滚。

### Q55. Docker 解决什么问题？你项目怎么用的？
**一句话：**  
把「环境不一致、多进程互相拖死、小机器资源失控」三件事一次解决。

**展开（结合沐龙）：**  
1. **环境一致**：开发/测试/正式同一 Dockerfile（Python 3.11 slim + 依赖），少出现「我机器能跑、服务器缺包」。  
2. **进程隔离**：一个镜像多种启动命令——`api`（8100）、`webhook`（交易信号）、`dingtalk-agent` 分容器；Webhook 卡死不影响管理 API。  
3. **资源可控**：Compose 给 `mem_limit`（如 api 768m、webhook 384m），小规格 ECS 不至于一个进程吃光内存把整机拖挂。  
4. **数据持久**：`data`/`log` 挂 volume，容器重建日志和业务数据还在。  
5. **健康检查**：容器内 curl `/api/health`，Compose/`restart` 策略配合，挂了能自愈。

**追问「镜像怎么构建」：**  
- 前端**禁止**在 ECS 里 `npm build`（小内存易 OOM），必须在 GitHub Actions/本地先打出 `frontend/dist`，再 COPY 进镜像；Dockerfile 里会检查 `index.html` 是否存在。  
- 国内构建用阿里云 apt、清华 PyPI，加快且更稳。

### Q56. GitHub Actions 流水线怎么做？（重点题）
**一句话：**  
测试机可自动/半自动部署；正式机只走手动 `workflow_dispatch`，发布=构建前端 → 打发布包 → SSH 远端安装 → 健康检查 → 打版本可回滚。

**流程口述：**  
1. **触发**：正式机 Actions 手动选 `deploy` / `list` / `rollback`，避免 push 误发生产。  
2. **CI 侧**：checkout → 校验 shell 语法 → `build-frontend.sh` 产出 dist → 打包代码与脚本。  
3. **CD 侧**：用 Secrets 里的 SSH 密钥连 ECS → `remote-ci.sh` / `deploy.sh` 拉起 Compose → 等 health。  
4. **版本**：每次正式发布打 `YYYYMMDD-HHMMSS-<git短sha>`；服务器留镜像 + 发布包（默认近 5 版）；回滚切版本，不是 `docker cp` 改文件。  
5. **并发组**：同环境 `concurrency` 防止两次发布交叉踩踏。

**测试 vs 正式：**  
- 测试 ECS：`deploy.yml`，迭代快。  
- 正式 ECS：`deploy-prod.yml`，人工确认；策略见「禁止热更」。

**Secrets 一般有啥：**  
`SSH_HOST` / `SSH_USER` / `SSH_PRIVATE_KEY` / 端口；密钥不进仓库。

### Q56b. 为什么禁止生产热更？（很容易被追问）
**答：**  
以前用过 `docker cp`、局部 scp、hotfix 脚本「先改文件再 restart」——结果经常半套版本：路由新、策略旧、前端 dist 回退、依赖没装上，线上故障多。  
所以正式服**唯一路径**：本地改 → 提交推送 → Actions 全量 Deploy。紧急例外也要事后全量对齐。这体现的是工程纪律，不是偷懒。

### Q57. Nginx 在你链路里干什么？
**一句话：**  
对外 HTTPS 入口：静态/页面反代到应用，API 同源转发，证书与安全头放这层。

**结合项目：**  
- 浏览器访问域名 → Nginx（443）→ `proxy_pass` 到本机 `127.0.0.1:8100`（容器映射出来的 API）。  
- 前端 dist 可由应用托管，或 Nginx 直接 `root` 静态目录；关键是 **同源**，少踩 CORS。  
- 可在 Nginx 做：TLS、gzip、限流、超时、大 body（Webhook）、隐藏后端端口。  
- 改配置后 `nginx -t` 再 reload，避免直接挂掉入口。

**和 Docker 分工：**  
Nginx 在宿主机管「入口」；Docker 管「业务进程」。别把证书和业务进程绑死在一个容器里（小项目也可 all-in-one，但我们现网是宿主机 Nginx + 容器 API）。

### Q58. 小规格 2c2g / 小内存 ECS 怎么撑住？
**一句话：**  
少占内存、少在机器上编译、能降级就降级，先保证「能演示/能跑通」再谈性能。

**具体手段：**  
1. **构建外移**：npm/vite 放 Actions，ECS 只拉镜像/起容器。  
2. **限制并发与连接池**：Gunicorn workers 偏少、DB 连接池收紧。  
3. **Compose mem_limit**：防止单个服务 OOM 杀邻居。  
4. **功能降级**：智能商城演示可用嵌入式向量库/JSON 回退、Mock 支付物流。  
5. **缓存**：行情/观察库指标磁盘缓存，少打外部 API。  
6. **镜像瘦身**：slim 基础镜像、`.dockerignore`、清 apt 缓存。

### Q59. Linux / Shell 自动化你具体写过什么？
**答：**  
围绕发布与验收，而不是「装个机」：  
- `deploy.sh` / `remote-ci.sh`：远端安装、起停 Compose。  
- `build-frontend.sh`：统一前端构建。  
- `versioning.sh`：list / rollback。  
- `verify-prod.sh`：健康检查（8100/关键接口）。  
- 日志：`docker logs`、挂载的 `log` 目录排查 Webhook/交易。  
- `.env` 注入密钥与 DB；正式机 MySQL 可走宿主机已有实例（Compose profile 区分）。  

和「禁止热更」配套：脚本服务于**可重复发布**，不是给人手改容器内代码开后门。

### Q59b. 镜像、容器、Compose 三者关系？（快问）
**答：**  
镜像=只读模板；容器=镜像跑起来的进程实例；Compose=声明多容器怎么组网、挂卷、限资源、依赖顺序。我们一个 `backpack-quant` 镜像，Compose 起 api/webhook/agent 多个容器。

### Q59c. 容器挂了怎么查？
**答：**  
`docker ps -a` 看退出码 → `docker logs` → healthcheck 是否失败 → 看 mem_limit/OOM → 宿主机 `df`/`free` → 对照最近一次发布版本。业务上先看 `/api/health` 和交易/Webhook 日志。

### Q59d. 蓝绿/滚动你怎么理解？和你们现状差在哪？
**答：**  
理想是新版本起来、探活通过再切流量。我们当前小规格 ECS 更接近「打版本包 + Compose 重建 + 健康检查 + 可 rollback」；流量入口仍是单机 Nginx。规模上去再谈多机与负载均衡——体现不过度设计。
