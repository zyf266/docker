# 张运繁 · 二面线下：项目经验 / 跨部门沟通 / 项目管理

> 面向：技术二面或业务/TL 线下考察「能不能扛事、能不能对齐人、能不能把事情推完」。  
> 锚点经历：同花顺（财报/数据）→ 邦业（考试系统 DRF+Vue）→ 沐龙量化（FastAPI+React 全栈 0→1）。  
> 口述结构统一用 **STAR**：Situation（背景）→ Task（你的目标）→ Action（你具体做了什么）→ Result（结果/数字/规范）→ Reflection（反思一句）。  
> 原则：**少形容词，多动作与边界**；不贬前司；冲突讲「对齐事实与优先级」，不讲人身。

## 30 秒定位（开场可先说）

我近三年交付偏「业务闭环」：从数据处理、考试后台，到量化平台从 0 到 1。二面你们关心的三块——  
1）**项目经验**：我能讲清目标、取舍、线上结果；  
2）**跨部门沟通**：和产品/交易/运维对齐接口契约与验收标准；

# 一、项目经验（深挖真实性 + 主人翁）

### Q1. 挑一个你最有代表性的项目，讲 3 分钟

**标准答（沐龙量化）：**  
**S：** 需要一套可生产的量化 Web：信号进、跟单出、账户可看、发布可追溯。  
**T：** 我负责从 0 到 1 的全栈闭环（不只写脚本）。  
**A：**  
- 后端 FastAPI：Portal、观察库、交易所绑定、账面记账；  
- TradingView Webhook → 匹配策略/币种/周期 → 解密密钥 → 下单/dry-run；  
- 进程拆分：主 API / webhook / 钉钉 Agent，交易不被 LLM 拖死；  
- 发布：GitHub Actions → 正式服，**禁止热更**，Deploy 后按端口健康检查验收。  
**R：** 形成可演示、可运维的闭环；规范写进仓库（禁热更、验证门禁）。  
**收尾一句：** 您可以从「信号到下单」或「发布规范」任选一条追问，我都能落到字段和路径。

### Q2. 这个项目里你个人贡献边界是什么？哪些不是你做的？

**答：**  
我主责：**接口设计、跟单链路、Portal 前后端、部署拆分与发布规范**。  
策略信号内容来自 TradingView/业务方；交易所行情与撮合不在我们侧。  
我会明确说「配置谁定、执行谁做、验收谁点头」，避免「全都是我」被追穿。

### Q3. 项目中最大的技术难点？你怎么决策的？

**答（选一个深讲，推荐「路径隔离」）：**  
难点是 **交易低延迟路径 vs AI 评分/长轮询** 抢资源。  
对比方案：全塞一个进程 vs 多进程旁路。  
我选 **拆进程 + 评分 fire-and-forget**：交易口稳、可独立重启。  
代价是运维多几个容器，用 Compose/Actions 统一拉起，可接受。

**备选难点：** 观察库指标拉取贵 → 30 分钟磁盘缓存 + 进页不强制刷；密钥 RSA 落库只 mask 回显。

### Q4. 有没有失败或返工？你学到什么？

**答：**  
早期容易一次做全功能，联调期需求变、返工多。  
后来固定节奏：**先 MVP（能记账/能 dry-run）→ 再实盘开关 → 再加统计与体验**。  
线上问题先止血（降级/回滚），再把结论写进规范（例如禁热更），避免同一类事故。

### Q5. 如果重新做一遍，你会改什么？

**答：**  
1）接口契约更早用 OpenAPI/示例 JSON 冻结，减少前后端口头对齐；  
2）Webhook 鉴权（Token/HMAC）一开始就按生产标准，而不是后期补；  
3）里程碑验收清单模板化（健康检查、关键链路冒烟），减少「以为上了其实没验」。

### Q6. 同花顺 / 邦业经历怎么讲才不像注水？

**答（各 40 秒）：**  
- **同花顺：** 财报/行情类数据处理——清洗、校验、入库；练的是数据质量与时效，不是挂名跑数。  
- **邦业：** DRF+Vue3 考试/后台——权限、分页列表、前后端分离联调；练的是业务系统交付。  
两段证明我会在「数据管道」和「业务后台」两边落地；沐龙是把两端合成全栈闭环。

# 二、跨部门沟通（二面高频）

### Q7. 你怎么和产品 / 非技术同事对齐需求？

**答：**  
我不只听「要一个列表」，会追三件事：  
1）**用户是谁、成功标准是什么**（例如：进观察库要 3 秒内有数，还是必须最新 K 线）；  
2）**边界**（哪些状态人工配、哪些自动算）；  
3）**验收用例**（给 2～3 条：正常/无权限/失败提示）。  
对齐后我回一页「范围 + 不做清单 + 排期」，避免口头需求漂移。

### Q8. 举一个跨角色协作的真实例子

**答（Webhook 跟单 / 账面）：**  
**S：** 业务要用 TradingView 信号记账或跟单，入口还要兼容无端口域名。  
**T：** 我要把「信号字段、账户归属、是否真实下单」对齐清楚。  
**A：**  
- 和业务确认：策略名/币种/周期、开平方向、仓位是固定金额还是本金比例；  
- 和技术/运维确认：80 端口 Nginx 只反代 API，不改坏原站；  
- 我提供 dry-run 与正式 webhook 地址、样例 JSON，先演练再开实盘。  
**R：** 链路可复现；误操作风险用 dry-run 和权限（admin 账面）控住。

### Q9. 需求冲突时你怎么办？（产品要快 vs 你要稳）

**答：**  
先把冲突翻译成 **风险清单**：不做幂等会怎样、热更会怎样、没鉴权会怎样。  
给选项而不是只说「不行」：  
- A：本周上 MVP（只记账 / dry-run），风控项下周补；  
- B：本周上全量，但必须加 Token + 去重，工期多 X 天。  
让对方选，我执行并书面记下「已知风险谁签字」。  
量化里「禁热更、走 Deploy」就是用规范替临时人情。

### Q10. 和前端 / 同事意见不合怎么处理？

**答：**  
对技术分歧：用 **数据与约束** 裁决（超时、限流、安全、用户可感知延迟），不比嗓门。  
例：观察库「秒开」——我主张默认读缓存、手动刷新才 force；用「进页超时率」说明全量拉 K 线不可接受。  
对人：对事不对人；会上对齐结论，会后同步纪要，避免二次解读。

### Q11. 对方不回消息 / 协作方卡住，你怎么推进？

**答：**  
1）阻塞升级前先给 **最小可继续方案**（mock 数据、默认配置、先做我侧）；  
2）钉钉/邮件写清：缺什么、卡到哪天、影响哪个里程碑；  
3）超过约定 SLA 同步负责人，不是私下抱怨。  
目标是「事情往前走」，不是证明谁不对。

### Q12. 如何向领导汇报进度？（二面很爱听）

**答三句话结构：**  
1）**结论**：进度绿/黄/红；  
2）**事实**：本周完成了什么、差什么；  
3）**请求**：需要什么决策或资源（是否砍范围、是否延期）。  
不报流水账；风险提前说，不报喜不报忧。

# 三、项目管理能力（个人贡献者视角的「带事」）

> 你未必带过大团队——二面考的是 **能否把一件事从模糊推到可验收**。

### Q13. 你如何拆解一个中型需求？

**答：**  
1）目标与非目标（Out of Scope）；  
2）依赖（账号、密钥、域名、第三方 API）；  
3）里程碑：接口可调 → 联调通过 → dry-run → 生产开关 → 观测；  
4）每阶段验收标准（可勾选）；  
5）回滚/降级预案。  
沐龙里「账面 webhook」就是：先记账闭环，再谈实盘跟单。

### Q14. 如何排优先级？需求太多怎么办？

**答：**  
用简单矩阵：**影响面 × 紧急度 × 风险**。  
交易资金路径、安全、数据正确性 > 体验文案。  
同时在飞的事控制在 1～2 个主线；其他进 backlog 并告知「本周不做」。  
被加塞时问：「插队的话，原里程碑哪条延期或砍掉？」逼出显式取舍。

### Q15. 风险与质量你怎么管？

**答：**  
- 开发：本地冒烟 + 关键路径手测；前端改动要 build；  
- 发布：CI 全量部署，禁止服务器改代码；  
- 上线后：健康检查清单（端口、容器、关键 API）；  
- 线上事故：止血 → 复盘 → 固化成规则。  
这是个人项目管理里的「质量门禁」，不是空喊责任心。

### Q16. 估算工期准不准？延误了怎么办？

**答：**  
估算拆成「已知工作 + 缓冲（联调/环境 20%～30%）」。  
发现要延误： **提前 2～3 天** 同步，给调整方案（砍范围 / 加人 / 改期），不临上线才说。  
例：交易所签名联调常超预期，我会把「对接联调」单独估，不并进「写接口一天」。

### Q17. 你带过人或只是独立开发？

**答（诚实版）：**  
以独立交付和跨角色协作为主；沐龙上我定义接口契约、拆任务顺序、验收标准，相当于 **对事项负责的 Owner**。  
若问带团队：说明目前是 IC（个人贡献者）强项在端到端交付；到岗后可按团队规范做 Code Review、任务拆分带新人。

### Q18. 文档与知识沉淀怎么做？

**答：**  
关键路径写进仓库文档（维护教程、发布规范、接口说明）；  
运维命令可复制；  
禁止把密钥写进文档和 Git。  
目的：别人按文档能接手，降低「只有我知道」。

# 四、情景题（线下常临场演）

### Q19. 上线前一天产品要加一个「小需求」，你怎么说？

**答：**  
先确认是否真影响上线目标。  
若影响主路径：建议 **下个迭代**，或 tonight 只做开关默认关闭的配置，不做未测逻辑。  
若只是文案/展示：评估 1～2 小时可做则做，并说明不回归交易路径。  
底线：不把未验证改动塞进生产热更。

### Q20. 线上交易/记账异常，业务很急，你怎么组织？

**答：**  
1）**止血**：关实盘开关 / 切 dry-run / 限流，保护资金与数据；  
2）**定位**：按链路查（信号是否进、是否匹配配置、是否下单、库表是否写入）；  
3）**同步**：钉钉同步现状、影响范围、下次更新时间（如 30 分钟一次）；  
4）**修复**：走正规发布，不手改生产代码；  
5）**复盘**：根因 + 防再发（去重、监控、清单）。

### Q21. 两个需求都说自己最重要，你怎么站队？

**答：**  
不站人，站 **公司目标与风险**：资金安全与核心成交 > 锦上添花。  
把两边诉求写在同一页对比：用户影响、延期成本、技术风险，拉共同上级做一次 10 分钟决策。  
我执行决策并反馈进度。

### Q22. 你如何证明自己有「项目管理能力」而不是只会写代码？

**答（收束金句）：**  
我会把模糊需求变成 **有边界的里程碑、有验收的交付、有预案的上线**；跨部门时用契约和选项推进，而不是只说「我写完了」。  
沐龙从 0 到 1、发布规范与事故止血，是这件事的证明。

# 五、二面临场技巧（短）

| 技巧 | 做法 |
|------|------|
| 先结论 | 每题第一句先答「是什么/怎么办」 |
| 控时 | 主答 60～90 秒；细节等追问 |
| 用数字 | 「30 分钟缓存」「三进程」「禁热更」「dry-run」 |
| 露边界 | 主动说非你负责的部分，可信度更高 |
| 反问 | 结尾可问：「团队里跨部门需求一般谁做 Owner？」 |

### 建议你准备的 3 个「随身故事」（背熟）

1. **沐龙 0→1 + 禁热更规范**（项目经验 + 管理意识）  
2. **Webhook 与业务/运维对齐字段与 dry-run**（跨部门沟通）  
3. **交易与 AI 拆进程 / 线上止血再复盘**（优先级与风险管理）
