# B. 后端 Python / Django / DRF（JD 核心）

### B1. 你更熟 FastAPI，Django 行不行？

**答：**  
近期主力 FastAPI，但邦业考试系统用过 **Django REST Framework + Vue3**：序列化、鉴权、分页、ViewSet 套路熟悉。Django 强在 Admin、ORM、迁移、权限中间件；FastAPI 强在异步与类型校验。到岗后按团队规范写 DRF，业务建模和接口分层能力可直接复用，框架差异大概几天到两周能对齐。

### B2. 用 DRF 设计「资产列表」接口你会怎么做？

**答：**  
- Model：`Asset`（名称、类型、状态、所有者、当前版本号、创建/更新时间）  
- Serializer：列表瘦字段、详情含版本摘要；入参校验类型/大小/状态机合法值  
- ViewSet：`list/retrieve/create`；过滤（类型、标签、状态）、搜索、排序、分页  
- Permission：登录 + 对象级（只能看本部门/授权范围）  
- 返回统一结构，错误可定位（类似我们量化里 `ok` + `detail`）

### B3. ORM、迁移、事务你怎么用？

**答：**  
复杂查询用 `select_related`/`prefetch_related` 减 N+1；迁移走 `makemigrations`/`migrate`，生产禁手改库结构。审批通过「改状态 + 写流水」放同一事务；失败回滚。死锁就缩短事务、统一加锁顺序、条件走索引（同花顺/后台库经验同一套）。

### B4. 参数校验和权限控制怎么做？

**答：**  
DRF Serializer / 我们 FastAPI 用 Pydantic，本质都是边界校验。权限：JWT/Session 认人 → 角色（RBAC）→ 数据范围（本部门/仅自己）。敏感操作（发布、删除、过审批）二次校验。密钥、OSS 密钥不进前端。

### B5. 文件上传大文件怎么设计？（加分：OSS）

**答：**  
浏览器不直传业务机落盘（占带宽/磁盘）。推荐：**后端签发 OSS/S3 临时上传凭证 → 前端直传 → 回调/确认写入资产元数据与版本记录**。下载用签名 URL 限时。预览按类型：图片缩略图、视频转码异步任务。我们量化侧有文件/配置落盘与权限隔离经验，资产侧补上 OSS 签名链路即可。

# C. 业务：RBAC、审批、版本（JD 强调）

### C1. RBAC 和数据范围怎么理解？

**答：**  
RBAC：用户 → 角色 → 权限点（如 `asset:upload`、`asset:approve`）。  
数据范围：即使有 `asset:view`，也只能看「自己的 / 本部门的 / 项目内的」。实现上可在 QuerySet 层按 `owner_id`/`dept_id` 过滤，避免只藏按钮。沐龙 Portal 与管理端按角色分流，是同一思想。

### C2. 审批流状态机怎么设计？

**答：**  
状态例如：`draft → pending → approved/rejected → published`（可再加 `archived`）。  
转移表写死合法边；非法跳转直接 400。每次转移写 `ApprovalLog`（谁、何时、意见）。通过后触发：版本锁定、打标任务、通知。禁止「前端改个 status 字段就过审」——必须走审批接口。

### C3. 版本管理怎么做？

**答：**  
资产 1 : N 版本；上传生成 `version_no` 递增；`current_version_id` 指向生效版。回滚=把 current 指回旧版并记日志，物理文件尽量保留。并发上传用乐观锁或唯一约束 `(asset_id, version_no)`。

# E. AI / LLM / Agent / RAG（JD 核心加分）

### E1. 智能打标、内容识别你会怎么接模型？

**答：**  
上传完成 → 异步任务丢队列 → 调多模态/文本模型 → **结构化输出**（JSON：标签、类目、置信度）→ 落库为「待确认标签」→ 人工确认或自动过阈值。禁止模型结果直接覆盖正式标签（和商城「禁止 Agent 自动下单、必须确认」同一原则）。

### E2. Prompt、结构化输出、流式、上下文怎么做？

**答：**  
- Prompt：角色+约束+少样本+输出 schema  
- 结构化：JSON Schema / Tool Calling 强制字段  
- 流式：SSE/流式 API，前端逐字展示，提升体感  
- 上下文：只塞检索到的相关片段和当前资产元数据，控制长度；会话外置存储，避免一次塞爆  

我们 DeepSeek/钉钉链路里评分卡片、Tool Calling 都按这套控。

### E3. Agent、Tool Calling、MCP 你怎么理解？

**答：**  
Agent = 模型 + 规划 + 工具。Tool Calling：模型选工具（搜资产、写标签、提审批），服务端执行后把结果回填。MCP 是工具/资源的标准接入协议，方便把「检索、OSS、工单」挂成可插拔能力。我们商城做过接单/推荐/物流等工具，并强制人工确认；资产侧可做「检索→建议标签→提交审批」工具链。

### E4. Embedding、向量检索、RAG 怎么落地到资产库？

**答：**  
资产文本/OCR/标签 → Embedding → 向量库；查询时语义召回 TopK → 拼进 Prompt 做问答或推荐相似素材。注意：权限过滤要在检索层做（不能召回无权限资产）。我们有 Chroma/RAG 向量记忆、以图搜品（图→向量/多模态）经验，可迁到「以文搜图、以图搜图」。

### E5. 你用什么 AI 编程工具？如何保证质量？

**答：**  
Cursor 等做生成与改码；流程是：拆任务 → 写清验收 → 实现 → **跑通验证（测试/构建）** → 再合入。Harness：沙箱、禁止生产热更、密钥不进记忆。不把 AI 产出当真理，Code Review + 冒烟必须有。

# F. 异步任务 / Redis / 消息队列（JD 加分）

### F1. 为什么打标/转码要 Celery，而不是请求里同步调模型？

**答：**  
模型慢、易超时，同步会堵 Worker、拖垮上传接口。应：**接口快返回 task_id → Celery/队列异步跑 → 前端轮询状态**。失败重试、死信/失败表。我们采集侧用 Kafka 削峰、量化侧 Webhook 快返回+评分旁路，是同一思想；到资产项目用 Celery+Redis/RabbitMQ 更贴 Django 生态。

### F2. 任务重复执行怎么办？

**答：**  
至少一次语义下要幂等：同一 `asset_version_id` 的打标任务用唯一键；成功写结果表；重试不覆盖「已人工确认」的标签。

# I. 场景综合题（二面爱问）

### I1. 设计「上传 → 识别打标 → 审批 → 发布」全链路

**答：**  
1. 前端直传 OSS，回调写 `asset`+`version(draft)`  
2. 投递 `tagging` 任务，结果进「建议标签」  
3. 用户确认标签后点提交 → `pending`，通知审批人  
4. 审批通过 → `approved/published`，当前版本切换，写日志  
5. 发布后可被语义检索；权限贯穿列表与检索  
失败：任务重试；审批驳回回 draft；全程可审计。

### I2. 模型胡乱打标怎么控？

**答：**  
结构化输出 + 置信度阈值 + 默认待确认 + 审核流；关键资产人工必审；Prompt 限制标签词表；bad case 回流优化。

### I3. 你最大的技术难点？迁移到本岗位的启发？

**答：**  
量化里 Webhook 低延迟和 LLM 抢资源——用进程拆分、旁路异步、缓存。资产系统同样：上传/列表要快，识别/打标要异步隔离，AI 不能堵主链路。
