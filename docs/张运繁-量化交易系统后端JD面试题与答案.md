# B. 系统设计与架构（JD 职责 1）

### B1. 用一张图讲你的量化后台架构

**答：**  
三层：**React SPA** → **FastAPI 主 API（8100）**；旁路两个独立进程——**webhook_service（8005）** 做低延迟跟单执行，**tradingview_bot（Flask 5001）** 做 TV 信号解析与钉钉多群路由。数据以 **MySQL（SQLAlchemy）** 为主，热点指标有磁盘/内存缓存。设计要点是 **交易路径与 AI/重计算路径解耦**，避免评分或回测拖死下单。

### B2. 为什么要拆多进程，而不是一个 FastAPI 扛所有？

**答：**  
1. Webhook 要快回、稳，不能和 DeepSeek 评分、长轮询监控抢 GIL/重启窗口；  
2. TV 只打固定端口，主 API 发版不影响信号入口；  
3. 故障隔离、可独立扩缩。代价是运维多几个容器/进程，用 `start_trading_stack` + Compose/Actions 统一拉起。

### B3. 若从 0 设计「多用户跟单交易系统」，你会怎么拆模块？

**答：**  
- **接入层**：Webhook/鉴权/限流；  
- **配置层**：用户-策略-标的-仓位-风控参数；  
- **执行层**：统一下单抽象（各交易所 Adapter）；  
- **账本层**：成交、持仓、PnL；  
- **观测层**：日志、钉钉、健康检查。  
边界清晰：接入不直接持有密钥明文；执行只读解密后的会话；账本写库要幂等。我们 Portal 观察库 + exchange binding + trades 就是这套的轻量落地。

### B4. 同步 vs 异步、线程 vs 协程，你项目怎么选？

**答：**  

| 模型 | 场景 |
|------|------|
| asyncio（Uvicorn） | 主 API、定时任务、`to_thread` 包阻塞 IO |
| Flask 同步 + 线程 | TV Bot：解析快、钉钉推送；评分 fire-and-forget |
| daemon Thread | 快讯/盘口监控长轮询 |
| 策略 Thread + 独立 event loop | 单策略实例隔离运行 |

原则：**IO 密集协程/线程；CPU 重活多进程；交易关键路径尽量短、少依赖。**

### B5. 单体够用吗？什么时候上微服务/分库？

**答：**  
当前体量单体 + 多进程足够。微服务适合团队边界清晰、独立扩缩、发布频率差异大时；分库分表是单表量级、热点、合规隔离到瓶颈再上。面试别吹已经上了——要说清 **触发条件与代价（分布式事务、调用链、运维）**。

# C. 量化交易系统与交易接口（JD 职责 2、4）

### C1. 讲一条 TradingView 信号到下单的完整路径

**答：**  
TV POST → Portal `/tv-webhook`（或 5001/8005 对应入口）→ 解析 strategy / symbol / timeframe / 方向 → 匹配 `connected` 观察库配置 → 服务端解密交易所密钥 → 按仓位模式算保证金 → 市价开/平 → 可选挂 TP/SL → 写 `portal_trades`。同向已有仓可跳过；支持 dry-run 只演练不下单。

### C2. 策略名 + 币种 + 周期为什么要三元组匹配？

**答：**  
同一用户多策略、多周期并行；三元组精确定位配置，降低误跟单。风险点：多用户同名策略可能撞车——应用 webhook token / 用户级密钥隔离加固。

### C3. 幂等：TV 重复推送怎么办？

**答：**  
信号 ID 或内容摘要去重；库表约束兜底；已处理状态不重复下单/不重复钉钉。配合限流，防止洪峰打满执行层。

### C4. Webhook 安全怎么做？密钥怎么存？

**答：**  
生产应：HTTPS、HMAC/Token、必要时 IP 白名单、审计日志。密钥 **RSA 加密入库**，接口只回 mask；仅下单/验资时服务端解密。日志禁止明文 key/私钥。我们规范里还禁止生产热更，降低人为泄露与错发。

### C5. 对接 OKX / Hyperliquid / Binance 的差异与抽象？

**答：**  
- OKX：API Key + Secret + Passphrase，REST 签名；  
- HL：钱包私钥，链上/专用 API；  
- Binance：签名与限流规则又不同。  
业务层统一「绑定 → 验资 → 下单 → 持仓/余额」；Adapter 消化协议差异。余额为 0、精度、最小名义价值要在下单前拦截。

### C6. REST 和 WebSocket 在交易系统里怎么分工？

**答：**  
REST：下单、查余额、配置 CRUD、Webhook 回调。  
WebSocket：行情推送、订单/成交推送、降低轮询。  
注意：WS 断线重连、心跳、本地状态与 REST 对账；关键成交以成交回报/REST 查询为准，不单信推送一次。

### C7. 观察库「状态配置」趋势/反弹/空头怎么设计？

**答：**  
三套独立条件（如 2h/4h 站上日线 WMA15、中强 MA30、长强 MA200），按 **趋势 → 反弹 → 空头** 优先级取首个全满足者；都不满足显示 —。市场级批量配置，新标的默认继承，避免每个币手配一遍。

### C8. 单币收益率为什么用「收益 / 仓位」而不是固定本金？

**答：**  
全账户用固定本金（如 500 万）看账户级回报；筛单币时仓位占用不同，用该币开仓 margin 均值做分母，收益率更贴近「这笔本金赚了多少」，避免小仓位大波动被账户本金稀释失真。

# D. Python / 数据结构 / 设计模式（JD 需求 1）

### D1. GIL 是什么？量化里为何还用多线程？

**答：**  
GIL 同一时刻一个线程执行字节码，纯 CPU 多线程加速有限。我们大量是 **网络 IO**（交易所、LLM、钉钉），阻塞时会释放 GIL，多线程能提高吞吐。回测/重计算才考虑多进程。

### D2. 常见数据结构你项目里怎么用？

**答：**  
- dict：配置、实例注册表、缓存；  
- 列表/队列：成交序列、待推送；  
- set：去重、已处理信号；  
- 有序结构/时间窗：监控窗口统计。  
选结构先想访问模式：按 key 查用 hash；要顺序与窗口用 list/deque。

### D3. 举两个设计模式落地

**答：**  
- **适配器**：各交易所统一下单接口；  
- **策略/配置驱动**：观察库状态 profiles、TV 路由按 strategy 分支；  
- **单例**：监控服务 `get_*_instance` 保证全局一个后台线程。  
不硬套名词，强调「变化点隔离」。

### D4. JD 写 Flask，你主栈 FastAPI，怎么答？

**答：**  
主 API 用 FastAPI（异步、Pydantic、OpenAPI）；**TradingView 信号 Bot 就是 Flask**，同步快解析 + 线程旁路评分/钉钉。两种都用过：Flask 适合轻量同步入口，FastAPI 适合异步 API 与类型校验。到岗按团队栈写即可。

### D5. Java 要求怎么接？

**答：**  
近期交付以 Python 为主；本科与工程里接触过 Java 基础（集合、并发概念、Spring 生态了解）。服务端共性是接口设计、事务、线程安全、部署。若团队 Java 主力，我能以业务与架构能力切入，语法与框架按规范补齐；诚实不装成三年 Java 主力。

# E. API / WebSocket 产品经验（JD 需求 2）

### E1. 如何设计一套可联调的交易相关 API？

**答：**  
资源路径清晰（绑定交易所、观察库、成交列表分开）；统一响应（成功数据 + 可定位错误）；Pydantic/Schema 校验杠杆、仓位非法值直接 400；分页与筛选（平台/币种/策略）；敏感字段永不回传明文。OpenAPI/Swagger 方便前端与测试。

### E2. 交互产品里 WebSocket 要注意什么？

**答：**  
鉴权（连接时带 token）、心跳、重连退避、消息幂等与序号、服务端推送背压。前端断线提示与 REST 兜底刷新。交易展示类可用 WS 推余额/成交，下单仍可用 REST 便于超时与重试语义清晰。

### E3. 前后端分离职责？

**答：**  
后端：鉴权、风控规则、一致性、密钥；前端：筛选、卡片、图表、交互。契约稳定后并行开发；Portal 账户卡片、交易清单、状态配置弹窗都是契约驱动。

# F. 数据库与存储（JD：MySQL / MongoDB）

### F1. 为什么交易账本用 MySQL 而不是只写 JSON？

**答：**  
成交、配置要查询、统计、约束与备份；MySQL + ORM 适合结构化账本。JSON/磁盘适合缓存与轻状态（指标缓存、告警 state）。我们 `portal_trades`、bindings、watch configs 走库；热点 K 线指标可缓存。

### F2. 索引与慢查询你怎么处理？

**答：**  
按查询条件建联合索引（如 user_id + platform + created_at）；避免 `%` 前导模糊；分页用主键/时间；解释执行计划。统计窗口尽量在内存对已筛结果聚合，或预聚合表。

### F3. 事务：下单与写成交怎么保证？

**答：**  
理想：交易所成功回执与本地账本同逻辑事务（先下单成功再 commit 本地，失败标记 error/可重试对账）。不能把「没下单却记成功」或「下成功却没落库」常态化——需要对账任务与人工兜底。

### F4. MongoDB 你会用在哪？

**答：**  
适合半结构化日志、灵活信号原文、研究笔记。强一致资金账本仍偏 MySQL。若 JD 要求 Mongo，可做信号审计库或文档型配置，与 MySQL 账本并存。

# G. 工程化 / 运维开发（JD 标签）

### G1. 本地到生产怎么发布？

**答：**  
本地改代码验证 → commit/push → **GitHub Actions Deploy to Prod** → 容器重建。**禁止**生产机 docker cp / 手改 py。Deploy 后查健康检查与关键端口（如 8100/5001 等）。

### G2. Docker 里依赖安装超时怎么治？

**答：**  
钉版本（如 ccxt 钉死已知版本）、镜像源、分层缓存、减少无约束最新解析。根因是解析大版本树或网络，不是盲目加 timeout。

### G3. 日志与排障习惯？

**答：**  
按模块打关键路径（webhook 命中、下单请求/回执、跳过原因）；密钥 mask；线上先看最近错误与是否幂等误杀。监控类服务可独立日志文件。

### G4. 配置与密钥管理？

**答：**  
`.env` / 密钥加密字段；不进仓库；生产改 Webhook 等经确认改环境而非改代码。权限：管理端与 Portal 角色分流。

# I. 场景题 / 手撕思路（二面常问）

### I1. 交易所限流了，下单队列怎么设计？

**答：**  
令牌桶/漏桶按 API weight；失败分类（可重试 429 vs 业务拒绝）；指数退避 + 抖动；关键减仓可插队；持久化队列防进程挂丢单；与本地订单状态机对齐。

### I2. 如何避免重复开仓？

**答：**  
下单前查持仓/本地意图锁；信号幂等键；同向同策略冷却时间；DB 唯一约束。

### I3. 行情延迟或丢包怎么处理？

**答：**  
WS + REST 校准；超时标价不交易或降级只告警；时间戳校验过期信号丢弃。

### I4. 写伪代码：计算窗口收益率

**答：**  
```text
pnl = sum(trade.pnl for trade in window)
cap = mean(open.margin) if 单币 else account_initial
return_pct = pnl / cap * 100 if cap > 0 else None
```
强调分母定义要和产品语义一致。
